## P0-1 · 她每天 11:30 准时醒，而且是硬跳变

### 实测

拿 `evaluateSleep` 跑完整 24 小时（`bedtimeHint = '23:30'`，`energy = 100`，无互动）：

```
06:30 p=1.000 dist=  420 睡
...
11:20 p=1.000 dist=  710 睡
11:30 p=0.000 dist= -720 醒      ← 一步从 1.000 跳到 0.000
11:40 p=0.000 dist= -710 醒
```

**这比它替换掉的那张固定表还硬。** 原来的表至少是 7:00 醒；现在是 11:30 醒，
而且概率在一分钟内从 1 掉到 0。

### 根因

`evaluateSleep` 的唯一时间输入是 `minuteDistance(now, bedtimeHint)` ——
**「距离就寝时间多远」**。模型里根本没有「起床」这个维度。

于是睡着之后 `dist` 一路涨，`p` 单调升到 1.000，**永远达不到 `WAKE_HYSTERESIS = 0.22`
的醒来条件**。真正让她醒过来的，是 `minuteDistance` 里那两行环绕：

```ts
if (distance < -12 * 60) distance += 24 * 60
if (distance > 12 * 60) distance -= 24 * 60
```

`dist` 越过 +720 的那一刻被折成 -720，`p` 随之从 1 掉到 0。

**净效果：醒来时刻 = `bedtimeHint` + 12 小时，精确固定，与精力、睡了多久、
前一天怎么样全部无关。** 这正是这轮要消灭的流水线，只是换了个位置。

### 我这边的责任

上一份说明里我要求的验收扫描是「从 20:00 到 02:00」——**那恰好是这个模型唯一
正常工作的窗口**。早上从来没被扫过。这条是我的说明写窄了，不是你漏做。

**新的流程规矩**（写进 `notes.md`）：**任何周期性状态机的验收扫描必须覆盖完整周期。**
半个周期的曲线好看，说明不了另外半个。

### 改法

**1. `DayPlan` 增加 `wakeHint`。** 和 `bedtimeHint` 对称，同样是当天生成、同样只是倾向。
生成提示词里要让这两个值一起变化（熬夜的一天配晚起，早睡的一天配早起，
偶尔来个通宵或者睡到下午），而不是各自独立随机。

**2. 丢掉环绕距离，改用绝对时刻。** 这是跳变的直接来源。
每天算出**今晚的就寝时刻**和**明早的起床时刻**两个真实 `Date`，
距离就是普通减法，不存在任何折返点，`p` 在整个 24 小时里连续。

**3. 睡意由两端合成。** 接近就寝时上升，进入睡眠窗口后维持，接近起床时下降。
两个 sigmoid 相乘即可，各自锚在自己的时刻上。

**4. 起床时刻也要受状态影响**，否则只是把固定闹钟从 11:30 挪到 wakeHint：

- **睡得晚就起得晚**：记录实际入睡时刻（持久化），实际起床倾向 = `wakeHint` +
  「比计划晚睡了多久」的一部分补偿
- **没睡饱会赖床**：起床时精力恢复得不够，往后拖一点
- 保留日级抖动和现有迟滞

**5. 顺带复核一个量级。** 现在 `energyShift = (50 - energy) * 1.8`，
精力满时把入睡推迟 90 分钟（`bedtimeHint 23:30` 实测约 01:40 才睡着）。
加上起床维度后重新看这个系数是否还合适 —— 不要现在就调，先把结构改对。

### 验收断言

```
★ 完整 24 小时扫描中，相邻两次求值的 p 变化不超过 0.25
   这条直接钉死跳变；现在会在 11:20→11:30 处以 1.000 的落差跑挂

★ 醒来时刻不是「就寝 + 固定偏移」
   两天用不同的 bedtimeHint / wakeHint 组合，
   醒来时刻之差 ≠ 就寝时刻之差

★ 晚睡会晚起
   同一份 wakeHint，实际入睡晚两小时 → 醒来时刻明显后移（但不是也后移两小时）

睡饱了会自然醒，不依赖任何环绕
   睡眠窗口内精力持续恢复 → p 在接近 wakeHint 时连续下降并跨过迟滞门槛

日程描述与睡眠状态不矛盾（第四轮已有行为，改完要仍然成立）
```

前三条必须能在改动前跑挂。

## P0-2 · `applyElapsed` 用当前瞬间的睡眠状态覆盖整段空档

`src/main/chat.ts:191`：

```ts
this.persona.applyElapsed(now, this.sleepState?.().asleep ?? false)
```

`asleep` 取的是**此刻**的状态，却被用来结算**整段 `[updatedAt, now]`**。

- 晚上 23:00 关掉 app，第二天中午 12:00 打开：13 小时，此刻醒着 →
  `energy -= 26`。她睡了一夜，回来却精疲力尽。
- 上午 10:00 关掉，凌晨 01:00 打开：15 小时，此刻睡着 →
  `energy += 60` 直接封顶。她「睡」了一整个下午。

这条直接抵消掉本轮 `energy` 修正的收益，而且离线时间越长错得越离谱。

### 改法

把 `[updatedAt, now]` 按睡眠窗口**分段积分**：落在睡眠窗口内的小时按恢复算，
其余按消耗算。用 P0-1 的 `bedtimeHint / wakeHint` 锚点粗切就够，**不需要精确到分钟**
——这里要的是符号正确，不是数值精确。

跨越 48 小时以上的部分沿用现有做法，不必逐段推演。

### 验收断言

```
★ 跨夜空档结算后精力上升，而不是下降
   23:00 → 次日 12:00（13 小时）→ energy 高于起始值

★ 白天空档结算后精力下降
   10:00 → 22:00（12 小时）→ energy 低于起始值

跨越整夜加半天的空档，方向由两段净额决定，不由结算时刻决定
```

前两条必须能在改动前跑挂 —— 现在第一条会反向。
