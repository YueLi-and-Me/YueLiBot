# 第七轮：该看看她说出来的是什么了

第六轮**全部通过**，我独立跑了七天连续模拟 + 一组「聊到深夜」的场景验证：

- 七天入睡/醒来偏差 -20 ~ +20 分钟（残差来自设计内的 ±12 分钟 jitter），相邻最大跳变 `0.0630`
- `WAKE_HYSTERESIS` 从 0.22 改成 0.4，偏差仍为 0 —— **补偿确实是 `logit()` 推导的，不是填的常量**
- 睡眠债在正常流程真的会触发：聊到就寝后 30/90 分钟 → 晚睡 45/75 分钟 → 次日晚起 15/30 分钟
- 就寝实际落点跨 22:20–01:20，三小时

模型这块可以收尾了。这轮换一件事。

---

## P0-1 · 六轮下来，没有一轮检查过她说出来的内容

翻一遍前六轮的验收断言：时刻、概率、跳变、去重键、冷却、偏差、退出码——
**全部是结构性的，没有一条是关于「她说出来的话好不好」。**

结果就是：日程生成的**机制**已经被验证得很扎实（持久化、判重、回退、校验、方差），
但**生成出来的 `slots` 到底写了什么，从头到尾没有人看过一眼**。

我在代码里见到的唯一一条实例是 fallback 里的 `'在整理今天的小心情'`。
如果模型产出的都是这种质感，那么这七轮做的所有事——每天不一样的作息、
两端 sigmoid、睡眠债、赖床——在用户那里的实际体验仍然是**一句平淡的废话**。

**机制正确不等于产品成立。** 这一轮要补的就是这个缺口。

### 要交付什么

不是断言，是**给人看的材料**。跑真实生成，把下面三样贴出来：

**1. 连续三天的完整 `DayPlan` 原文** —— 所有 `slots` 的 `from / doing / mood`，
一个不漏，加上 `theme`、`bedtimeHint`、`wakeHint`。我要看三天读起来是不是三个不同的日子。

**2. `describeSchedule()` 在六个时刻的实际输出** —— 建议取：
清晨刚醒 / 上午 / 午后 / 傍晚 / 睡前犯困 / 凌晨睡着时。
这是真正注入 prompt 的那段文字，它的质感直接决定她的回答。

**3. 一组真实对话** —— 在上述不同时段各问她一次「你在干嘛」，贴出她的原话。
这是唯一能证明整条链路（生成 → 注入 → 回答）真的接通的东西。

> **前置：先加一个时间注入开关。** 现在只有 `YUELI_FORCE_SLEEP` 这个布尔量，
> 要验「凌晨三点问她话」只能真的改系统时间——那会影响用户机器上的其他软件，
> 不能要求用户这么做。
>
> 加 `YUELI_NOW`（绝对时刻或相对偏移均可），让主进程和 `core/` 里所有取当前时间的
> 地方统一走它。**只在这一处读 `Date.now()`**，其余全部由参数传入——
> `core/` 本来就是这个约定（`daily.ts` 开头就写了「时间一律从参数传入」），
> 主进程侧照做即可。
>
> 这个开关本身就是资产：以后验节日、验纪念日、验离线补偿都要用它，
> 不必每次改系统时间。

### 判据

人读的，不是断言：

- 三天的 `slots` 要能看出是**三个不同的日子**，不只是时间点不同、措辞同质
- `doing` 要具体到能引出对话（「在把桌面上的便签重新排了一遍」而不是「在做自己的事」）
- `mood` 要真的影响语气，不是摆设
- 睡前那段要能看出困意，凌晨那段要能看出是被叫醒的

**如果读下来平淡、三天像同一天、或者 `doing` 全是「在整理心情」这类空话，
那就是提示词没做够——先报告，贴出你认为不合格的部分，不要自己反复重跑直到抽到一次好的。**

一次抽样好看不算数，要的是稳定的质感。

## P1-2 · 起床时间的方差远小于就寝

第六轮真实生成的七天，实际醒来时刻：

```
07:30  07:40  07:50  08:00  07:30  09:50  08:00
```

七天里六天挤在 **07:30–08:00**（30 分钟内），只有一天到 09:50。
而就寝跨了三小时。

用户要的「今天睡懒觉」**一周只出现一次**，而且是被前一天熬夜带出来的，
不是她自己想睡懒觉。

### 改法

只动 `wakeHint` 的生成提示词，**不要碰睡眠模型**（它只是忠实执行 hint）：

- 明确要求起床时间和就寝时间**各自**都要有方差，不是只让起床跟着就寝走
- 给出具体情形：睡够了但就是不想起、周末赖到十点多、偶尔天没亮就醒了睡不回去
- 和 P1-3（第六轮那条）一样，把**前一天的 `wakeHint`** 也作为输入

### 验收

再跑一次连续七天，贴出 `wakeHint` 表。判据：起床时间跨度至少 90 分钟，
且至少有一天的晚起**不是**由前一天晚睡造成的。

## P1-3 · 偏差断言没覆盖真实路径

第六轮的校准断言固定了 `jitter = 0.5`，所以测出来偏差 ≤ 10 分钟。
但真实路径的 `jitter` 由日期哈希决定，会带来 ±12 分钟——我七天实测是 **-20 ~ +20 分钟**。

这**不是缺陷**，jitter 是设计内的。但断言测的是一条真实运行时不会走的路径，
所以它保护不了「有人不小心把 jitter 的幅度调大十倍」这类改动。

### 改法

保留现有的固定 jitter 校准断言（它验证的是补偿推导，仍然有价值），
另加一条**真实路径**的断言：连续七天不固定 jitter，
断言每天的入睡/醒来偏差都在 ±30 分钟内。

这条的作用是给 jitter 幅度加一个上界，防止有人后来把随机性调到破坏 hint 语义。

## P1-4 · 整个项目最大的未验证面：真实屏幕和真实语音

> **⚠ 这一项需要用户配合，你无法独自完成。**
> 视觉要有人真的开着 Steam、真的在玩游戏；TTS 要有人决定用哪家服务并提供 Key
> （方舟没有 `/audio/speech`，已验证 404）。
> **你的职责是：把该接的线接好、把自检脚本写好，然后明确说明「等待用户提供 X」。**
> 不要用合成图、假音频或猜测的服务商把这一项标记成完成。

这条不属于日程，但已经悬了很多轮，趁这轮一起收掉。

**视觉链路从来没有对着真实屏幕跑过。** 所有验收都用的是 `sharp` 画的合成 SVG
（死亡画面、Steam 库、农场、敏感文件夹）。合成图是干净的、居中的、高对比的；
真实的 Steam 窗口有滚动条、悬浮提示、半透明遮罩、多语言混排。

**TTS 的 HTTP 往返从来没有成功过一次。** 方舟没有 `/audio/speech` 端点（已验证 404），
所以整条语音链路——请求、缓存、IPC 传输、口型驱动——只跑过本地假数据。

### 要做的

**视觉**：打开 `VISION_ENABLED=1`，真的把 Steam 开着、真的开一个游戏，
让它自然触发一次识别。贴出：触发原因（`frame-change` 还是 `idle-glance`）、
模型原始输出、脱敏后的描述、她最终说的话。
**如果一次都没触发，那本身就是结论**——把 `visionStats` 的 `byReason` 贴出来，说明卡在哪一道闸。

**TTS**：找一个真的提供 OpenAI 兼容 `/audio/speech` 的服务配上去，跑通一次完整往返：
请求 → 拿到音频 → 缓存命中 → IPC 传到渲染层 → 口型跟随。
贴出各段耗时和缓存命中的证据。**配不通就明说配不通**，不要用假音频糊过去——
那正是这条至今没被验证的原因。

## 不要做的事

沿用前六轮全部禁止项，另加：

- **不要为了让内容好看而反复重跑生成直到抽中一次。** 要的是稳定质感，
  抽样好看是最糟糕的一种假通过。
- 不要为了 P1-2 去改睡眠模型。模型只是忠实执行 hint，方差问题在生成侧。
- 不要用合成图代替 P1-4 的真实屏幕验证。合成图已经验过了，再验一遍没有增量。
- 不要为了让 TTS「有东西可看」而伪造音频数据。

## 交付要求

- `npx vitest run` 全绿并报出新的用例总数
- P0-1 的三样材料**全文贴出**，不要摘要
- P1-2 的七天 `wakeHint` 表
- P1-4 两项各自的真实结果，或者明确的「没跑通，卡在哪」
- 有不同意的项写明理由，不要默默跳过
