# 第四轮：把固定日程换成生成式生活

前三轮共 15 项**全部复审通过**。这轮换掉 `src/core/schedule/daily.ts` 那张写死的
`SCHEDULE` 表——第三轮说明里预告过的那件事。

顺带修两处第三轮遗留（P1-4、P1-5），都很小。

---

## 为什么要换

现在的 `SCHEDULE` 是一条流水线：每天 21 点必定「窝着刷手机」，23 点必定「准备睡了，
在赖床」，0 点准时熄灯。**跑第二天你就把她的一生看完了。**

可预测等于没有生活感。真人的日常是：今天睡懒觉、今天熬夜、今天出门了一整天、
今天什么都没干。入睡也不是到点关灯，而是「困了」「还想再聊会儿」「今天太累了」
这些东西合出来的结果。

目标：**每天不一样，且入睡时机由状态推出来，不是由时钟宣布。**

---

## ⚠ 动手前必须先看：`energy` 现在的语义是错的

这轮的设计要拿「精力」当参考输入。但我查了 `src/core/persona/state.ts`，
它现在的动力学是：

- 每说一轮话 `energy -= 0.4`
- `applyElapsed` 每空闲一小时 `energy += 4`

也就是说 **`energy` 实际度量的是「最近被聊了多少」，不是「累不累」**。
白天没人理她，精力会一路涨满；跟你聊了一晚上，精力见底。

如果直接拿它驱动入睡，涌现出来的行为是「**聊得越起劲越早睡**」——
和你要的「聊得起劲会撑着不睡」正好相反。

### 所以先做这件事

给 `energy` 补上**时间维度的自然消耗**，让它同时反映「醒了多久」：

- 醒着的时间本身要消耗精力（比如每清醒一小时 `-2`），而不是只有说话才消耗
- `applyElapsed` 的 `+4/小时` 恢复**只在睡眠状态下生效**；醒着时的空闲不叫休息
- 说话的 `-0.4/轮` 保留，但它现在是「附加消耗」而不是唯一消耗

改完之后 `energy` 才是「距离上次睡觉过了多久 + 消耗了多少」的合成量，
才配当入睡的参考输入。

**验收断言：**

```
★ 醒着不说话也会掉精力（现在会涨）
   连续清醒 6 小时、零对话 → energy 明显下降

睡眠期间才恢复
   睡眠 8 小时 → energy 明显回升
   清醒 8 小时 → 不回升

说话是附加消耗，不是唯一消耗
   同样清醒 3 小时，聊了 50 轮的比没聊的更低
```

第一条必须能在改动前跑挂。

## P0-1 · 每日生成一份当天的日程

### 产物

一份当天的计划，落库，**同一天内只生成一次**——否则 prompt 里她的行程会在对话中途
自己变，前后矛盾。

结构上仍然是「若干时段」，但**段数、时间点、内容每天都不同**：

```ts
interface DayPlan {
  /** 本地日期 YYYY-MM-DD，用于判重 */
  date: string
  slots: Array<{
    /** 起始时刻，小时+分钟，允许 8:40 这种非整点 */
    from: string
    doing: string   // 第一人称描述，注入 prompt
    mood: string    // 这个时段的语气倾向
  }>
  /** 计划入睡时间。只是倾向，不是命令 —— 见 P0-2 */
  bedtimeHint: string
  /** 今天大概是个什么样的一天，一句话。给做梦和日记用 */
  theme: string
}
```

### 生成时机

**懒生成**：任何需要日程的地方发现「今天还没有计划」就生成一份。
不要开新定时器，不要在启动时抢跑——启动时 LLM 可能还没配好。

### 输入

给模型的材料（**都要脱敏，规则同视觉链路**）：

- 日期、星期几、是否节日/纪念日（现有节日表）
- 人格四轴的**自然语言描述**（`describePersona`），**不要给数字**
  —— 这条是既有约束，别在这里破例
- **昨天的 `theme`**，用来避免连续两天雷同（「昨天出门逛了一天」→ 今天倾向宅着）
- 最近几天的交互密度（聊得多/几乎没聊）

### 硬要求

**1. 必须失败安全。** LLM 调不通、超时、返回垃圾 → **退回现在这张固定表**。
保留 `SCHEDULE` 作为 fallback，不要删。桌宠不能因为日程生成失败就不知道自己在干嘛。

**2. 对外接口不变。** 下面三个是既有消费方，签名和语义都不许动：

- `describeSchedule(now)` —— `prompt.ts:80` 在用
- `activitiesBetween(from, to)` —— 离线补偿在用
- `sleep.ts` 里那个唯一的睡眠访问器 —— 第三轮专门为这次改造留的口子，**从这里接**

**3. 生成的内容要有约束。** 不许出现：具体人名、地名、需要「真的出门」才成立的事
（她是桌面上的角色，不是有身体的人）。这一层在提示词里写死，并在本地做一次校验——
**提示词不是边界，这条规矩这个项目已经吃过教训。**

### 验收断言

```
★ 同一天内重复请求返回同一份计划，不会重新生成
   连续三次取当天计划 → 只调用一次模型，三次结果全等

★ 生成失败时退回固定表，而不是让日程为空
   provider 抛错 → describeSchedule 仍返回非空且合理的描述

跨天会生成新的一份
   date 变化 → 重新生成

计划描述里不含数字化的人格数值
   生成用的 prompt 中 grep 不到 intimacy/energy 等字段的原始数字
```

## P0-2 · 入睡由状态推导，不是到点宣布

### 要点

`bedtimeHint` 只是**倾向**。真正是否入睡，由几件事合出来：

- 距 `bedtimeHint` 还有多久（主要项）
- 当前 `energy`（修好语义之后的那个）
- **刚刚是不是在聊天**——聊得起劲就往后拖，这是你明确要的那条
- 一点随机抖动，让同一组状态不总是同一分钟睡着

### ⚠ 最容易做砸的地方

**不要做成阈值机器人。** `if (energy < 20) sleep()` 只是把一套固定规则换成另一套
更复杂的固定规则，那样什么都没改善。

要的是**倾向随状态平滑移动**：早了几乎不可能睡，晚了几乎必然睡，中间是个逐渐上升的
概率带，`energy` 和「刚聊过」把这条带整体前移或后移。判定要**带迟滞**——
一旦入睡就不要因为一次抖动马上又醒（这个项目在记忆遗忘曲线上已经用过 FREEZE/REVIVE
的迟滞做法，照那个思路来）。

**还有一条：她该在真正睡着之前先表现出困。** 从「开始犯困」到「睡着」之间要有一段
她会说「有点困了」「再聊十分钟就睡」的窗口——这段过渡比入睡本身更有生活感。

### 验收断言

```
★ 同样的时刻，不同状态下入睡与否不同
   同一时刻 + 高精力 + 刚聊过 → 未入睡
   同一时刻 + 低精力 + 长时间无交互 → 已入睡

★ 入睡不是阈值触发
   在过渡窗口内多次求值，结果不是全 false 突然全 true
   （即存在既非「必醒」也非「必睡」的中间带）

入睡后带迟滞，不会立刻醒回去
   刚入睡 → 精力小幅回升 → 仍然是睡着

睡前有可观测的「犯困」阶段
   入睡前一段时间内，状态可查询为 drowsy，且 describeSchedule 会提到困意
```

第二条是这轮的核心，必须能真的区分开——**如果实现是阈值，它一定会跑挂。**

## P1-3 · 离线补偿要能读历史日程

`activitiesBetween(from, to)` 现在是拿固定表逐小时推演。换成生成式之后，
如果你离开三天，那三天的计划**根本不存在**（懒生成只在需要时才产生当天的）。

处理方式，按优先级：

1. 有存下来的历史 `DayPlan` 就用真的
2. 没有就用 fallback 固定表推演——**不要为补叙历史去补生成三天的计划**，
   那既慢又是编造
3. 超过 48 小时的部分维持现有做法（不逐段叙述，说「好久不见」更自然）

**验收**：离线 3 天且无历史计划时，`activitiesBetween` 仍返回合理的非空序列。

## P1-4 · 场景观察不该挤掉事件观察（第三轮遗留）

`game-scene` 和 `game-event` 现在都走 `priority: 'normal'`，共吃 30 分钟冷却。
她随口说完一句「他在种田」，接下来半小时里你死一百次她都不会开口。

**事件是时效性的，场景是填充性的**，让填充挤掉时效是反的。

改法（不要新加一层节流，那是第二轮踩过的坑）：给场景观察一个**更高的开口门槛**，
比如当天预算已用掉一定比例后就不再为场景开口，把余量留给事件。
`game-event` 的判定完全不变。

**验收**：预算余量充足时 scene 可开口；余量紧张时 scene 被拦而 event 仍可开口。

## P1-5 · 修掉报告与实现对不上的地方（第三轮遗留）

上一轮报告里写「实际看到**睡衣**闭眼立绘」。生图管线的 `KEEP_IDENTICAL` 明确禁止
改服装，`sleepy` 只是同一个身体上的面部差分，**不存在睡衣**。

如果实际资产里真的出现了服装变化，那是生图那边漏了约束，要报出来；
如果只是描述写岔了，以后不要这样写——**没核过的细节不要写进报告**。

## 不要做的事

沿用前三轮全部禁止项，另加：

- **不要删 `SCHEDULE` 固定表。** 它是 fallback，也是离线补叙的兜底，不是遗留代码。
- 不要把人格数值原样塞进日程生成的 prompt。四轴一律走 `describePersona` 的自然语言，
  这是既有硬约束。
- 不要为了日程生成新开定时器。用现有的 tick，懒生成。
- 不要把「入睡」写成单个阈值比较。见 P0-2。
- 不要为了让 `activitiesBetween` 好看而回溯生成历史日程。编造过去比含糊带过更糟。
- 不要在这轮碰视觉链路的解析、脱敏或上下文校验。P1-4 只动开口门槛。
